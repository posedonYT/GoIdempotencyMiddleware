# План реализации: Idempotency-middleware для `net/http` (Go)

Версия плана для MVP: **только in-memory хранилище**, только стандартная библиотека, ноль внешних зависимостей.

> **Главное правило проекта:** каждую строчку ядра вы пишете и отлаживаете сами. В подсказках ниже я даю скелеты и идеи, а не готовые решения. Если вы не можете объяснить строку вслух, она не должна попасть в репозиторий.

---

## 0. Что мы строим

### Проблема

Клиент отправил `POST /payments`, сервер выполнил списание, но ответ потерялся (таймаут, обрыв сети). Клиент повторяет запрос, и деньги списываются дважды.

### Решение

Клиент добавляет заголовок `Idempotency-Key: <уникальная строка>`. Middleware запоминает результат первого выполнения и при повторе с тем же ключом **не вызывает хендлер**, а возвращает сохранённый ответ.

### Поведение (контракт библиотеки)

| Ситуация | Что делает middleware |
|---|---|
| Метод не `POST`/`PATCH` (настраивается) | пропускает запрос без изменений |
| Заголовка нет | пропускает запрос (или `400`, если включён режим `Required`) |
| Ключ новый | помечает ключ «в процессе», вызывает хендлер, сохраняет ответ |
| Ключ уже выполнен, запрос тот же | отдаёт сохранённый ответ + заголовок `Idempotent-Replayed: true` |
| Ключ уже выполнен, **запрос другой** | `422 Unprocessable Entity` |
| Ключ в процессе (первый запрос ещё работает) | `409 Conflict` (позже: опция ожидания) |
| Хендлер вернул `5xx` или запаниковал | запись удаляется, клиент может повторить |
| Тело запроса слишком большое | `413` |

Коды `400/409/422` соответствуют IETF-драфту *The Idempotency-Key HTTP Header Field*. Референс по поведению: документация Stripe API про idempotent requests.

### Что НЕ входит в MVP

Redis/Postgres, метрики, tracing, стриминговые ответы (SSE, WebSocket, `Hijack`), trailers. Всё это явно записывается в README в раздел «Ограничения».

## 2. Диаграмма состояний записи

Нарисуйте её на бумаге до написания кода.

```
              Acquire (атомарно)
  нет записи ───────────────────► IN_PROGRESS
      ▲                              │      │
      │ Release                      │      │ Complete
      │ (5xx, panic, ошибка,         │      ▼
      │  не влезло в лимит)          │   COMPLETED ──(TTL истёк)──► нет записи
      └──────────────────────────────┘
```

Правила:
- Переход «нет записи → IN_PROGRESS» делает **ровно один** запрос. Это и есть защита от гонки.
- Из IN_PROGRESS можно выйти только двумя путями: `Complete` или `Release`. Третьего нет, иначе ключ «зависает».
- У IN_PROGRESS тоже есть срок жизни (lock timeout), чтобы упавший процесс не блокировал ключ навсегда.

## 3. Дизайн интерфейса `Store`

Интерфейс определяется на этапе 2, но продумайте его заранее: он определяет, насколько легко потом добавить Redis.

```go
type State int

const (
    StateInProgress State = iota + 1
    StateCompleted
)

type Response struct {
    Status int
    Header http.Header
    Body   []byte
}

type Entry struct {
    State       State
    Fingerprint string    // sha256 хэш запроса (hex)
    Response    *Response // не nil только в StateCompleted
}

type Store interface {
    // Acquire атомарно: если ключа нет (или он истёк), создаёт запись
    // IN_PROGRESS и возвращает acquired=true. Иначе возвращает
    // текущее состояние существующей записи и acquired=false.
    Acquire(ctx context.Context, key, fingerprint string) (e Entry, acquired bool, err error)

    // Complete сохраняет ответ и переводит запись в COMPLETED.
    Complete(ctx context.Context, key string, resp Response) error

    // Release удаляет запись IN_PROGRESS (хендлер не дал кэшируемого результата).
    Release(ctx context.Context, key string) error
}
```

Почему так:
- `Acquire` объединяет «проверить» и «вставить» в один вызов. Если бы были отдельные `Get` и `Set`, между ними другой запрос успел бы вставить свой ключ. Для Redis это превратится в `SET key value NX`, для Postgres в `INSERT ... ON CONFLICT DO NOTHING`. Интерфейс будет честным для всех бэкендов.
- Метод ожидания (`Wait`) намеренно не включён: в Redis его нет, там нужен polling. На этапе 8 мы сделаем ожидание необязательным.
- TTL хранилище получает через опции конструктора, а не в аргументах методов.

### Этап 1. Разведка `net/http` (1–2 дня)

Прежде чем писать библиотеку, поймите, как устроен `ResponseWriter`. Эти эксперименты в репозиторий не коммитятся (папка `scratch/` в `.gitignore`).

**Теория**
- `http.Handler` — интерфейс с единственным методом `ServeHTTP(w http.ResponseWriter, r *http.Request)`.
- Middleware — функция, которая принимает хендлер и возвращает новый хендлер: `func(http.Handler) http.Handler`.
- `ResponseWriter` — интерфейс из трёх методов: `Header()`, `Write([]byte)`, `WriteHeader(int)`.
- Порядок работы: заголовки выставляются **до** первого `WriteHeader`/`Write`. Если вызвать `Write` без `WriteHeader`, сервер неявно отправит `200`. Заголовки, изменённые после этого, клиент не увидит.
- `r.Body` — это `io.ReadCloser`, читается **один раз**. Прочитали, значит поток закончился.

**Делаем (мини-эксперименты)**
1. Напишите middleware-логгер, который печатает метод и путь и вызывает следующий хендлер.
2. Расширьте его: обёртка `ResponseWriter`, которая запоминает статус и считает записанные байты. Убедитесь, что статус `200` по умолчанию выставляется при первом `Write`.
3. Прочитайте `r.Body` в middleware через `io.ReadAll`, затем вызовите хендлер, который тоже читает тело. Увидите пустое тело. Исправьте через `r.Body = io.NopCloser(bytes.NewReader(data))`.
4. Запустите сервер через `httptest.NewServer` и вызовите его из теста.

**Подсказка**
```go
type statusWriter struct {
    http.ResponseWriter       // встраивание: все методы «пробрасываются» вниз
    status int
}

func (w *statusWriter) WriteHeader(code int) {
    w.status = code
    w.ResponseWriter.WriteHeader(code)
}
```
Встраивание интерфейса в структуру — ключевой приём Go, поймите его хорошо.

**Проверь себя:** почему `Write` без `WriteHeader` даёт `200`? Что увидит клиент, если выставить заголовок после `Write`?

### Этап 3. Recorder — перехват ответа (2 дня)

Это ядро библиотеки: нужно одновременно отдать ответ клиенту и сохранить его копию.

**Теория**
- Два подхода: **буферизация** (копим всё в памяти, отправляем в конце) и **write-through** (пишем клиенту сразу и параллельно копируем). Берём write-through: клиент получает ответ без задержки.
- Заголовки нужно **скопировать в момент `WriteHeader`**. Метод `Header()` возвращает живую `map`, и хендлер может её изменить позже, а копия должна отражать то, что реально ушло клиенту. `http.Header` имеет метод `Clone()`.
- `WriteHeader` можно вызвать несколько раз, но эффект имеет только первый. Ваш recorder должен вести себя так же.
- `Write` без предшествующего `WriteHeader` означает статус `200`.
- Лимит размера: если тело больше `MaxBodySize`, перестаём копировать и помечаем ответ «слишком большой для кэша». Клиенту при этом всё отдаём полностью.
- **`Unwrap()`**: если ваш тип имеет метод `Unwrap() http.ResponseWriter`, то `http.NewResponseController(w)` сможет «достучаться» до оригинального writer'а и вызвать `Flush`, `SetWriteDeadline` и т.д. Без этого обёртка ломает стриминг.

**Делаем**
1. `recorder.go`: структура с полями `status`, `header` (снимок), `body bytes.Buffer`, `wroteHeader bool`, `overflow bool`, `limit int`.
2. Методы `Header()`, `WriteHeader()`, `Write()`, `Unwrap()`.
3. Метод `result() (Response, ok bool)`, где `ok == false`, если было переполнение.
4. Тесты через `httptest.NewRecorder()` как нижний writer.

**Подсказка по `Write`**
```go
func (r *recorder) Write(p []byte) (int, error) {
    if !r.wroteHeader {
        r.WriteHeader(http.StatusOK) // неявный 200 и снимок заголовков
    }
    // 1) сначала пишем клиенту, 2) потом копируем в буфер,
    // но только ту часть, которая реально записалась (n)
    n, err := r.ResponseWriter.Write(p)
    // TODO: проверить лимит и скопировать p[:n]
    return n, err
}
```

**Проверь себя:** почему копию заголовков нельзя сделать в конце? Что случится, если хендлер вообще ничего не пишет (пустой `204`-ответ)?

### Этап 4. Отпечаток запроса и ключ (1 день)

**Теория**
- **Fingerprint** отвечает на вопрос «это тот же самый запрос?». Клиент мог по ошибке переиспользовать ключ для другой операции, и тогда отдавать ему старый ответ опасно.
- Состав: метод, путь с query, тело. Опционально: выбранные заголовки.
- Хэш: `sha256.Sum256(data)`, затем `hex.EncodeToString(sum[:])`. Хранить хэш, а не само тело: экономит память и не держит чувствительные данные.
- Разделители между частями (`method + "\n" + path + "\n" + body`), иначе `"ab"+"c"` и `"a"+"bc"` дадут одинаковый хэш.
- **Область видимости (scope).** Ключи двух разных пользователей не должны пересекаться: иначе пользователь B может получить ответ, предназначенный пользователю A. Решение: итоговый ключ в хранилище = `scope + "\x00" + clientKey`, где scope берётся из пользовательской функции (`WithScope(func(*http.Request) string)`) — например, ID пользователя или API-токена. Это один из самых частых вопросов о безопасности такой библиотеки.
- Валидация ключа: не пустой, длина до 255, только печатаемый ASCII. Иначе `400`.
- Чтение тела безопасно только с лимитом: `http.MaxBytesReader(w, r.Body, limit)`. При превышении ошибка приводится к `*http.MaxBytesError` (`errors.As`) → `413`.

**Делаем**
1. `fingerprint.go`: функции `fingerprint(r *http.Request, body []byte) string` и `validateKey(string) error`.
2. Функция `readBody(w, r, limit) ([]byte, error)`, которая читает и восстанавливает `r.Body`.
3. Table-driven тесты: одинаковые запросы дают одинаковый хэш; разный метод/путь/тело — разный; плохие ключи отклоняются.

**Проверь себя:** зачем в fingerprint входит query-строка? Что произойдёт без `scope` при двух клиентах, которые случайно выбрали ключ `"1"`?

### Этап 5. In-memory Store и главная гонка (3 дня)

Самый важный этап проекта.

**Теория**
- `map` в Go **не потокобезопасна**. Одновременная запись или запись+чтение приводит к панике `concurrent map writes` или к повреждению данных.
- `sync.Mutex`: `Lock()`/`Unlock()`, всегда в паре с `defer`.
- **Check-then-act гонка.** Неправильно: проверить ключ под локком, отпустить, вставить под локком. Между двумя блокировками другая горутина успеет вставить свой ключ, и хендлер выполнится дважды. Проверка и вставка идут под **одним** локком.
- **Не отдавайте наружу указатели на внутреннее состояние.** `Acquire` возвращает копию `Entry`. Иначе вызывающий код читает поля, пока другая горутина их меняет.
- Ленивое истечение: при `Acquire` проверяем `expiresAt` у найденной записи. Если время вышло, считаем, что записи нет.
- Часы: храните `now func() time.Time` в структуре (по умолчанию `time.Now`). В тестах подставляете управляемые часы. Это единственный надёжный способ тестировать TTL без `time.Sleep`.
- Не забывайте про время жизни IN_PROGRESS (`lockTimeout`): если процесс завис или упал, ключ освободится сам.

**Делаем**
1. `memory.go`: `type MemoryStore struct`, конструктор `NewMemoryStore(opts ...MemoryOption)`, внутри `mu sync.Mutex` и `items map[string]*item`.
2. Реализуйте `Acquire`, `Complete`, `Release`.
3. Опции: `WithTTL(d)`, `WithLockTimeout(d)`.

**Скелет `Acquire`**
```go
func (s *MemoryStore) Acquire(ctx context.Context, key, fp string) (Entry, bool, error) {
    s.mu.Lock()
    defer s.mu.Unlock()

    now := s.now()
    it, ok := s.items[key]
    if ok && !it.expiresAt.After(now) {
        delete(s.items, key)
        ok = false
    }
    if !ok {
        // TODO: создать item в состоянии IN_PROGRESS с expiresAt = now + lockTimeout
        // TODO: вернуть Entry{State: StateInProgress, Fingerprint: fp}, true, nil
    }
    // TODO: вернуть копию существующей записи, false, nil
}
```

**Тесты (обязательно)**
- Базовый сценарий: Acquire → Complete → Acquire возвращает COMPLETED с тем же ответом.
- Release возвращает ключ в «нет записи».
- TTL: подставили часы, прокрутили время, запись исчезла.
- **Гонка:** 100 горутин одновременно вызывают `Acquire` с одним ключом. Ровно одна получает `acquired == true`. Запускать с `-race`.

**Эксперимент для понимания:** временно уберите мьютекс и запустите тест с `-race`. Посмотрите на отчёт детектора, это полезно, чтобы потом не бояться его вывода.

**Проверь себя:** почему `Acquire` — один метод, а не `Get`+`Set`? Что изменится, если вернуть из `Acquire` указатель на внутренний `item`?

### Этап 6. Middleware: счастливый путь (2 дня)

**Теория**
- Конструктор возвращает `func(http.Handler) http.Handler`, так middleware встраивается в любой роутер (`net/http`, chi, gorilla/mux и другие).
- Порядок работы: проверить метод → достать и провалидировать ключ → прочитать тело → посчитать fingerprint → `Acquire` → вызвать хендлер через recorder → `Complete`.
- `Complete` и `Release` нужно вызывать с контекстом, не зависящим от отмены запроса: `context.WithoutCancel(r.Context())` (Go 1.21+). Иначе при отключении клиента запись не сохранится, а ключ повиснет.
- Replay: скопируйте сохранённые заголовки в `w.Header()`, выставьте `Idempotent-Replayed: true`, вызовите `WriteHeader(status)`, затем `Write(body)`.

**Делаем**
1. `idempotency.go`: тип `Middleware` (или функция `New(store Store, opts ...Option) func(http.Handler) http.Handler`).
2. Реализуйте счастливый путь: новый ключ → выполнение → сохранение → повтор → replay.
3. Тест: хендлер со счётчиком вызовов. Два одинаковых последовательных запроса: счётчик равен 1, ответы идентичны, второй содержит `Idempotent-Replayed`.

**Скелет**
```go
func New(store Store, opts ...Option) func(http.Handler) http.Handler {
    cfg := defaultConfig()
    for _, o := range opts { o(&cfg) }

    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            if !cfg.methods[r.Method] {
                next.ServeHTTP(w, r)
                return
            }
            // TODO: ключ, валидация, тело, fingerprint
            // TODO: Acquire и разбор результата (этап 7)
            // TODO: вызов next с recorder, Complete
        })
    }
}
```

**Готово, когда:** базовый тест зелёный, пример `examples/basic` запускается, и через `curl` можно увидеть replay.

### Этап 7. Ошибочные пути (3 дня)

Здесь видно зрелость библиотеки: большинство самодельных реализаций ломаются именно тут.

**Сценарии и решения**

| Ситуация | Решение |
|---|---|
| `Acquire` вернул COMPLETED, но fingerprint другой | `422` |
| `Acquire` вернул IN_PROGRESS | `409` + заголовок `Retry-After: 1` |
| Хендлер вернул `5xx` | `Release`, ответ клиенту отдан как есть |
| Хендлер запаниковал | `Release`, затем паника продолжается (`panic(p)` повторно) |
| Тело ответа превысило лимит | `Release` (кэшировать нельзя), ответ клиенту отдан полностью |
| Ошибка Store | политика: «fail closed» (`500`) или «fail open» (пропустить). Для платёжных операций честнее `500`, оформите это опцией и пропишите в README |
| Клиент отключился | хендлер продолжает работу, `Complete` всё равно вызывается (контекст без отмены) |

**Теория: паника и `defer`**
```go
completed := false
defer func() {
    if !completed {
        _ = store.Release(context.WithoutCancel(r.Context()), key)
    }
}()
next.ServeHTTP(rec, r)
// если дошли сюда — паники не было
// решаем: Complete или Release; в обоих случаях completed = true
```
Хитрость: в `defer` не нужно вызывать `recover()`. Достаточно флага `completed`: если паника пролетает мимо, флаг останется `false`, и ключ освободится. Паника при этом идёт дальше, и `net/http` сам её залогирует и закроет соединение.

**Теория: что кэшировать**
- Ответы `2xx` и `4xx` детерминированы, их кэшируем (повторная отправка вернёт тот же результат).
- `5xx` обычно означают временный сбой, клиент должен иметь право повторить. Не кэшируем по умолчанию. Опция: `WithCacheable(func(status int) bool)`.

**Делаем**
1. Реализуйте все строки таблицы.
2. Для каждой строки напишите тест (`t.Run` с понятным названием).
3. Тест на панику: хендлер паникует, `recover` стоит в тесте; после этого повторный запрос с тем же ключом **выполняется заново**, а не получает `409`.

**Проверь себя:** что будет с ключом, если хендлер паникует и флага `completed` нет? Почему `422` лучше, чем молча отдать старый ответ?

### Этап 8. Режим ожидания (2 дня, необязательный)

Вместо `409` второй запрос ждёт завершения первого и получает тот же ответ. Это удобнее клиентам.

**Теория**
- Канал `done chan struct{}` в записи. Когда запись завершается (`Complete` или `Release`), вызывается `close(done)`.
- **Закрытие канала работает как broadcast**: все горутины, ждущие `<-done`, просыпаются одновременно. Отправка значения разбудила бы только одну.
- Ожидание с отменой:
```go
select {
case <-it.done:
    // первый запрос завершился: повторяем Acquire
case <-ctx.Done():
    // клиент второго запроса отключился: возвращаем ошибку
case <-time.After(maxWait):
    // ждали слишком долго: 409
}
```
- После пробуждения **не** берём результат напрямую, а повторяем `Acquire` в цикле. Если первый запрос завершился успешно, получим COMPLETED. Если был `Release`, второй запрос станет новым исполнителем. Цикл ограничьте числом итераций.
- Для `time.After` в долгих циклах предпочтительнее `time.NewTimer` с `Stop()`, чтобы не копить таймеры.

**Делаем**
1. Расширьте `MemoryStore`: в `item` добавьте `done chan struct{}`.
2. Добавьте в интерфейс **опциональный** `type Waiter interface { Wait(ctx, key) error }`. Middleware проверяет `store.(Waiter)` через type assertion. Redis-реализация сможет не поддерживать ожидание.
3. Опция `WithWait(maxWait time.Duration)`.

**Главный тест проекта**
```go
func TestConcurrentSameKey(t *testing.T) {
    var calls atomic.Int32
    h := New(store, WithWait(5*time.Second))(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        calls.Add(1)
        time.Sleep(100 * time.Millisecond) // чтобы запросы гарантированно пересеклись
        w.Write([]byte("ok"))
    }))

    start := make(chan struct{})
    var wg sync.WaitGroup
    for range 50 {
        wg.Add(1)
        go func() {
            defer wg.Done()
            <-start // все стартуют одновременно
            // TODO: отправить POST с одним ключом, сохранить ответ
        }()
    }
    close(start)
    wg.Wait()

    // TODO: calls == 1, все 50 ответов имеют статус 200 и тело "ok"
}
```
Для режима без ожидания проверка другая: `calls == 1`, а каждый ответ либо `200` (оригинал или replay), либо `409`.

**Проверь себя:** почему закрытие канала, а не отправка в него значения? Почему после ожидания делаем `Acquire` заново?

### Этап 9. TTL, очистка и `Close()` (1–2 дня)

**Теория**
- Ленивое удаление (этап 5) освобождает память только при повторном обращении к ключу. Если ключ больше никто не запросит, запись останется в `map` навсегда.
- Решение: фоновая горутина-«уборщик» с `time.Ticker`, которая периодически проходит по `map` и удаляет истёкшие записи (под `mu`).
- **Утечки горутин.** Каждая запущенная горутина должна иметь способ остановиться. `Close()`: закрывает канал `stop`, уборщик выходит из цикла. Защитите `Close()` через `sync.Once`, чтобы двойной вызов не паниковал.
- Тикер нужно останавливать: `defer ticker.Stop()`.
- Ограничение размера (`WithMaxEntries`): без него `map` растёт бесконечно под нагрузкой. В MVP достаточно задокументировать риск, позже добавите вытеснение.

**Скелет уборщика**
```go
func (s *MemoryStore) janitor(interval time.Duration) {
    t := time.NewTicker(interval)
    defer t.Stop()
    for {
        select {
        case <-t.C:
            s.sweep()
        case <-s.stop:
            return
        }
    }
}
```

**Тесты**
- `sweep()` вызывается напрямую (без ожидания тикера) с подставленными часами.
- Утечки: после `Close()` горутина завершилась. Это можно проверить через `runtime.NumGoroutine()` до и после (с небольшим ожиданием) или счётчиком/каналом, закрываемым при выходе уборщика.

### Этап 10. API и опции (1 день)

**Теория: functional options**
```go

```
Этот приём позволяет добавлять настройки без поломки обратной совместимости: новые опции не меняют сигнатуру `New`.

**Итоговый набор опций MVP**

|---|---|

### Этап 11. Качество: race, fuzz, бенчмарки (2 дня)

**Теория и команды**
```bash
go test -race -count=1 ./...        # детектор гонок, обязателен
```

**Готово, когда:** покрытие ядра выше 85%, `-race` проходит стабильно при `-count=50`, бенчмарки записаны в README.

## 5. Частые ошибки (чек-лист ревью)

- [ ] Проверка и вставка ключа не разнесены на два захвата мьютекса.
- [ ] `Unlock` стоит в `defer`.
- [ ] Из хранилища не возвращаются указатели на изменяемое внутреннее состояние.
- [ ] Тело запроса читается с лимитом и возвращается в `r.Body`.
- [ ] Заголовки ответа копируются в момент `WriteHeader` (`Clone`).
- [ ] `Release` вызывается на всех путях, где результат не сохранён, включая панику.
- [ ] `Complete`/`Release` используют контекст без отмены клиента.
- [ ] В recorder есть `Unwrap()`.
- [ ] Ключ привязан к scope пользователя.
- [ ] Горутина-уборщик останавливается через `Close()`, повторный `Close()` безопасен.
- [ ] Тесты не используют `time.Sleep` для проверки TTL (только подставные часы).
- [ ] Каждый экспортируемый символ имеет doc-комментарий.
